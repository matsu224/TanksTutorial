ここではUnity公式チュートリアル「[Tanks Tutorial](https://learn.unity.com/course/tanks-make-a-battle-game-for-web-and-mobile?version=6.3)」を参考に開発を行いました。以下には開発を進めながら作成した備忘録を残します。

# Unity 開発備忘録 (Tanks Tutorial)

## Scene Setup (プロジェクト設定とシーン構築の基本)

### 基本的なビューとウィンドウの役割
* **Projectウィンドウ (パソコンのフォルダ/倉庫)**
  * プロジェクト内のすべての素材（画像、音、3Dモデル、スクリプトなど）を保管する場所。ここにあるのは単なる「ファイル」であり、フォルダの中にファイルを入れることはできても、ゲームオブジェクト同士の「親と子」のような階層構造を作ることはできない。
* **Hierarchyウィンドウ (設計図の階層/親子関係)**
  * 現在のシーン（画面）に配置されているオブジェクト（実体）を管理する場所。オブジェクトをドラッグ＆ドロップして「親・子・孫」といった階層構造（座標や回転の連動など）を作るための場所。

### タグ (Tag) とメタファイル (.meta)
* **Unityのタグ (Tag) とは**
  * オブジェクトをグループ分けするための名札機能。「Player」や「Enemy」といったタグを設定することで、スクリプトから特定の種類のオブジェクトだけを検索したり、当たり判定の相手を識別したりする際に使用する。
* **チーム開発で絶対やってはいけない「.metaファイルの無視」**
  * Unityは素材（アセット）を取り込む際、不可視の `.meta` ファイルを自動生成し、そこにIDやインポート設定を記録している。Gitなどのバージョン管理でこの `.meta` ファイルの共有を漏らしたり勝手に削除したりすると、シーン上のプレハブやスクリプトの参照（紐づけ）がすべて切れてプロジェクトが壊れるため厳重注意が必要。

### エディタのレイアウトと設定
* **推奨レイアウト (2 by 3)**
  * Sceneビュー（開発画面）とGameビュー（プレイヤー視点）を同時に確認できるため、配置やカメラの調整結果をリアルタイムに確認しやすい。
* **Projectウィンドウの視認性向上**
  * デフォルトの表示形式より、ウィンドウ右上の `⋮` (More) メニューから「One Column Layout」を選択すると階層が見やすくなる。
* **Sceneギズモの有効化**
  * オブジェクトを正確に配置・移動・回転させるため、Sceneビュー右上の「Orientation gizmo（方向ギズモ）」は常に有効にしておく。

### プロジェクトとシーンの管理
* **プロジェクトのクリーンアップ**
  * プロジェクト作成時に自動生成される不要なファイルや、使わない SampleScene は削除し、プロジェクト内を整理整頓しておく。
* **シーン専用フォルダの作成**
  * `Assets` フォルダ直下に `Scenes` フォルダを作成し、シーンファイル（`.unity`）はそこにまとめて管理するのが標準的な運用。
* **こまめな保存 (Ctrl+S / Mac: Cmd+S)**
  * 未保存の変更があるシーンは、Hierarchyウィンドウのシーン名の横にアスタリスク `*` が表示される。データを失わないよう定期的に保存する癖をつける。

### GameObjectとプレハブの基本操作
* **【重要】 配置直後のTransformリセット**
  * 空のオブジェクトやプレハブをHierarchyに追加した直後は、Inspectorから `Transform` の `Position` を `(0, 0, 0)` にリセットする。これによりワールド空間の原点が基準となり、後続の配置や計算時のバグを防ぐことができる。
* **Empty GameObject (空のオブジェクト) の活用**
  * Transformコンポーネントのみを持つオブジェクト。画面上には見えないが、複数のオブジェクトをまとめる「コンテナ（親オブジェクト）」として階層構造を整理するのによく使われる。
* **親オブジェクトと子オブジェクトの選択**
  * プレハブや複数のパーツで構成されたオブジェクトを移動・編集する際は、必ず「親オブジェクト全体」を選択して操作する。誤って子オブジェクトだけを動かすと、相対座標がずれて崩れてしまうため注意。

### カメラ (Camera) の操作と設定
* **Align With View (視点の同期)**
  * Sceneビューでカメラの構図（見え方）を決定した後、HierarchyでMain Cameraを選択し `GameObject > Align With View`（ショートカット: `Ctrl+Shift+F` / Mac: `Cmd+Shift+F`）を実行すると、Sceneビューの視点がそのまま実際のカメラ位置に反映される。
* **Sceneビューのフライスルー操作**
  * Sceneビュー上で「右クリックを押しながら WASD キー」を入力すると、FPSゲームのように空間を自由に移動できる。
* **カメラの投影方式 (Projection) の違い**
  * **Perspective (透視投影):** 人間の目と同じように遠近感（奥行き）がある。一般的な3Dゲーム向け。
  * **Orthographic (平行投影):** 遠近感がなく、距離に関わらずオブジェクトが同じ大きさで表示される。2Dゲームやクォータービュー（アイソメトリック）のゲームでよく使われる。表示範囲は `Size` プロパティで調整する。
* **カメラのクリッピング（見切れ）とローカルZ軸の調整**
  * カメラと対象物の間に地形などが挟まり、画面が不自然に切れてしまう（Near Clipに引っかかる）場合、カメラ自身の `Local` のZ軸（青い矢印の逆方向）へ下げる調整を行う。
  * ローカルのZ軸は「カメラの視線（奥行き）そのもの」であるため、ここを動かせばカメラの角度（見え方）を変えずに純粋に対象から距離だけを取ることができ、見切れを解消できる。

## Tank control (操作と物理演算の基本)

### エディタ設定とプレイモードの仕様
* **Playmode Tint (プレイモード時の色変更)**
  * `Edit > Preferences > Colors > Playmode tint` を設定することで、プレイモード中のエディタの背景色を変更できる。プレイモード中であることを視覚的に分かりやすくし、誤って編集してしまう（後でリセットされる）ミスを防ぐために重要。
* **【重要】 プレイモード中の変更保存ルール**
  * **Hierarchy上の変更:** プレイモード中にHierarchy（画面上の実体）の数値を変更しても、プレイモードを終了すると**すべて元に戻る（リセットされる）**。調整に便利だが、良い値が見つかったらメモしておく必要がある。
  * **Projectウィンドウ（アセット）の変更:** プレイモード中であっても、Projectウィンドウ内の大元のデータ（Prefabファイル、マテリアル、スクリプトなど）を直接編集した場合、**即座に永久保存され、プレイモード終了後も元に戻らない**。

### 物理演算 (Rigidbody) と当たり判定 (Collider)
* **Rigidbody コンポーネント**
  * オブジェクトに重力や物理演算を適用するためのコンポーネント。
  * **Constraints (制約):** 意図しない動きを防ぐために特定の軸の移動・回転を固定できる。例えば、車両が横転しないように `Freeze Rotation X/Z` を有効にしたり、空中に浮かないように `Freeze Position Y` を有効にしたりする。
* **Collider コンポーネント**
  * オブジェクトの「当たり判定（物理的な境界）」を定義する。これがないと他のオブジェクトをすり抜けてしまう。
  * **パフォーマンスの最適化:** 複雑な形状の `Mesh Collider` よりも、`Box Collider` や `Sphere Collider` などの単純な形状（プリミティブ）を使う方が計算負荷が低く、パフォーマンス面で有利。形状の大まかな近似で十分なことが多い。

### Sceneビューの便利な操作
* **Fキー (Frame Selected) とダブルクリック**
  * Hierarchyでオブジェクトを選択し、Sceneビュー上で `F` キーを押す（またはHierarchyでダブルクリックする）と、そのオブジェクトが画面の中央に収まるようにカメラが自動でズーム・移動する。正確な配置作業に必須のショートカット。
* **Sceneギズモを使った視点切り替え**
  * Sceneビュー右上のギズモの各軸（円錐形の矢印）をクリックすると、真上や真横からの視点に切り替わる。
  * **キューブ（中央）のクリック:** パース（遠近感）のある `Perspective` と、遠近感のない `Orthographic`（平行投影）を切り替えられる。当たり判定の微調整などは Orthographic の方が正確に行える。
  * **Freeモードへの復帰:** ギズモを右クリックして `Free` を選ぶと、通常の自由な視点操作に戻る。

### Prefab (プレハブ) の作成
* **ドラッグ＆ドロップによる自動プレハブ化**
  * Hierarchy上にあるGameObjectを、Projectウィンドウ（例えば Prefabs フォルダ）にドラッグ＆ドロップするだけで、そのオブジェクトの設計図として自動的に「Prefab化」される。
  * Prefab化されるとHierarchy上のアイコンが青いキューブに変わり、以降はProject内のPrefabを更新すれば、シーン上のすべての同じオブジェクトに変更が適用されるようになる。
* **Prefab (金型) と Instance (実体)**
  * Projectウィンドウにある大元のPrefabは「金型」であり、それをHierarchyにドラッグして配置したものは「Instance (実体/クローン)」と呼ばれる。実体側の数値を変更しても金型には影響しないが、金型を変更するとすべての実体に一斉に反映される。

### オーディオ (Audio) と演出
* **Audio Source の設定**
  * 音を鳴らすためのスピーカーの役割を果たすコンポーネント。エンジン音などの環境音は `Loop` にチェックを入れてループ再生させる。
  * スクリプトから `Pitch`（音の高さ）をランダムにわずかに変動させる（`Random.Range`）ことで、機械的なループ音に自然な揺らぎ（リアリティ）を持たせることができる。

## Camera and lighting (カメラとライティングの基本)

### オブジェクトの基本操作と複製
* **オブジェクトの複製 (Ctrl+D / Cmd+D)**
  * Hierarchy上でオブジェクトを選択し `Ctrl+D` (Mac: `Cmd+D`) で複製できる。複製したオブジェクトは元のオブジェクトと全く同じ位置に配置される。
* **スムーズな回転操作**
  * ツールを使ってオブジェクトを回転させる際、ハンドルを直線的にドラッグする (Drag in a straight line) ことで、よりスムーズで細やかな回転調整が可能になる。

### カメラの制御機構 (CameraRig)
* **Empty GameObject によるカメラ制御 (Parenting)**
  * 空のオブジェクト (Empty GameObject) を作成し、原点にリセットした上で「CameraRig（カメラ制御用の親コンテナ）」として機能させる手法がよく使われる。
* **階層化による制御の分離**
  * Main Camera を CameraRig の子オブジェクト (Child GameObject) に設定することで、スクリプトから CameraRig を動かした際、それに追従してカメラも動くようになる。移動とズーム（Size）の制御を分離でき、管理しやすくなる。

### カメラの背景設定
* **Background Type (背景の種類)**
  * カメラがズームアウトした際など、ゲームステージの範囲外が見えてしまう場合は、Main Camera の `Environment > Background Type` を調整する。
* **SkyboxからSolid Colorへの変更**
  * デフォルトの `Skybox`（空の表現）から `Solid Color`（単色塗りつぶし）に変更し、シーンの雰囲気に合わせた色（草や崖の色など）をスポイトで指定することで、見切れ部分の不自然さを解消できる。

### ライティングの基本と環境光
* **Directional Light (平行光源)**
  * 太陽光や月光をシミュレートし、シーン全体の雰囲気と影を決定する。
  * `Color` (色) と `Intensity` (明るさ) を変更することで、夕暮れや月夜などの時間帯を表現できる。
  * `Shadow Type` で影の品質を調整する。`No Shadows` (影なし)、`Hard Shadows` (カートゥーン調のくっきりした影)、`Soft Shadows` (より自然でリアルな影。デフォルトで推奨されることが多い)。
* **Environment Lighting (環境光)**
  * `Window > Rendering > Lighting` の Environment タブから設定。シーン全体の明るさ、コントラストを定義する。
  * `Environment Lighting Source` を `Color` に設定し、テーマ（月夜、ジャングル、砂漠など）に合った色を指定することで、空間のトーンが統一され、視認性とビジュアルの魅力が向上する。

## Firing shells (砲撃システムとUIの基本)

### Prefab (プレハブ) の編集
* **Prefab編集モード (Prefab Editing Mode)**
  * ProjectウィンドウにあるPrefabをダブルクリックすると、そのPrefab専用の編集画面（Prefab編集モード）に入る。シーン全体ではなく、対象のオブジェクト単体の中身（階層構造やコンポーネント）を安全に独立して編集・確認できる。

### Sceneビューの便利な操作と仕様
* **オービット (視点の旋回)**
  * Sceneビュー上で `Alt` (Mac: `Option`) キーを押しながらドラッグすると、選択しているオブジェクトを中心にカメラが旋回（オービット）する。砲身の先端など、3D空間で細かい位置合わせを行う際に非常に便利。
* **Create Empty (空のオブジェクト) の生成位置**
  * Hierarchyで何も選択せずに右クリックから `Create Empty` を実行した際、オブジェクトは「空間の原点 (X=0, Y=0, Z=0)」ではなく「**現在のSceneビューで見ている画面のど真ん中**」の空中に生成される。
  * ※特定のオブジェクトを右クリックして `Create Empty` を選んだ場合は、そのオブジェクトの子要素として生成される。
* **座標軸の基準 (Local と Global)**
  * Sceneビュー上部にあるトグルボタンで、移動・回転ツールの軸の基準を切り替えられる。
  * **Global (グローバル):** ワールド空間全体の絶対的な基準軸（常にYが上、Zが奥）。
  * **Local (ローカル):** そのオブジェクト自身の向きを基準とした軸（オブジェクトが上を向いていればY軸も上を向く）。砲身の向きに合わせて発射口を前方に微調整する場合は、必ず `Local` に設定してZ軸（青い矢印）を動かす。

### 発射口 (FireTransform) の設定
* **当たり判定 (Collider) との干渉に注意**
  * 砲弾の生成位置となる空のオブジェクト (FireTransform) は、戦車本体の `Box Collider`（当たり判定）の外（少し前方の空中）に配置すること。Colliderの内部に配置してしまうと、発射した瞬間に戦車自身と衝突して自爆してしまう。

### UI (ユーザーインターフェース) と Canvas
* **UIとCanvasの関係**
  * UnityでSlider（スライダー）などのUI要素を作成すると、自動的に `Canvas` という親オブジェクトが生成される。すべてのUI要素は、必ずこの Canvas の子オブジェクトとして配置される必要がある。
* **World Space UI (3D空間へのUI配置)**
  * 通常、Canvasの Render Mode は画面に直接張り付く形式（Screen Space）になっている。
  * Render Mode を `World Space` に変更すると、UIを3D空間内の1つの実体（頭上のHPバーやチャージゲージなど）として配置できるようになり、ゲームの世界に直接組み込める。
* **Rect Transform と配置 (Left, Right, Top, Bottom)**
  * 2DのUI要素の位置や大きさを制御する専用のコンポーネント。
  * `Top`, `Bottom`, `Left`, `Right` などのプロパティは、「親の指定範囲（アンカー）を基準として、内側に向かってどれくらい余白（オフセット）を取るか」を意味する。数値を `0` にすると、親の端にぴったりくっつくように端まで広がる。

### スライダー (Slider) のカスタマイズ
* **チャージゲージとしての利用**
  * スライダーをプレイヤーが操作するUIではなく、「チャージ状態を示すゲージ」として使う場合、Sliderコンポーネントの `Interactable` (操作可能) のチェックを外す。
  * `Direction` を `Bottom To Top` (下から上へ) に設定することで、力が溜まっていく視覚効果を作れる。
  * ※ `Min Value` (最小値) と `Max Value` (最大値) を設定する際、**必ず先に Max Value を設定してから Min Value を設定する**（Minが現在のMaxを上回ると自動で0にリセットされてしまう仕様のため）。

### コンポーネントの設定と紐づけ
* **Inspectorの整理**
  * Inspector内の各コンポーネントの `▼` (折りたたみ) を閉じて画面を整理することで、スクリプトへのオブジェクトのドラッグ＆ドロップ（紐づけ）作業がスクロールなしでスムーズに行える。
* **スクリプトへのアサイン**
  * スクリプト（TankShooting）内で設定された公開変数に対し、Prefab（砲弾）、Hierarchy上のオブジェクト（発射口、UIスライダー）、コンポーネント（Audio Source）を正しくドラッグ＆ドロップして紐づけることで、初めてシステムとして機能する。

## Health system (ヘルスシステムとレイヤーの基本)

### Inspectorの整理とコンポーネント管理
* **コンポーネントの並べ替えと整理**
  * Inspector内のコンポーネントは、ドラッグ操作や右上の `⋮` (More) メニューの `Move Up` / `Move Down` で並べ替えが可能。変更が頻繁なスクリプトを下に配置したり、物理演算系 (Rigidbody, Collider) をまとめたりすると作業効率が上がる。
  * ※ `Transform` コンポーネントは全オブジェクトの必須項目であるため、常に一番上に固定される。
* **【重要】 プレイモード中の値のコピー＆ペースト**
  * プレイモード中の数値変更は終了するとリセットされるが、良い設定値が見つかった際、コンポーネント右上の `⋮` メニューから `Copy Component` を実行し、プレイモードを終了した直後に `Paste Component Values` を実行することで、調整した数値を簡単に本番データへ反映できる。

### Layer (レイヤー) の概念と設定
* **Layer (レイヤー) とは**
  * シーン内のオブジェクトを特定のグループに分類するための機能。主に「特定のグループ間でのみ物理的な衝突判定や影響（爆発の吹き飛ばしなど）を有効にする」や、「特定のグループだけをカメラに映す/映さない」といった高度な制御を行うために不可欠な設定。
* **子オブジェクトへのLayer一括適用**
  * 親オブジェクトのLayerを変更した際、子オブジェクトにも同じLayerを適用するか聞かれるダイアログ (`Yes, change children`) が表示される。当たり判定や物理演算の対象を正しく機能させるためには、階層全体にまとめて適用することが一般的。

### UI (ユーザーインターフェース) の応用
* **放射状 (Radial) のUIゲージ**
  * UIスライダーは直線的な動きだけでなく、画像設定を応用することで、中心から円形に増減する360度のゲージとしても表現できる。

### Particle System (パーティクルシステム)
* **エフェクトの調整とプレビュー**
  * 爆発や炎などを表現するコンポーネント。`Start Speed` (初速)、`Start Size` (初期サイズ)、`Color over Lifetime` (時間経過による色の変化) などのプロパティを調整して見た目を作り込む。
  * 調整中は、Sceneビュー上に表示されるParticlesオーバーレイの `Restart` をクリックすることで、ゲームを再生しなくてもエディタ上で即座にエフェクトの動きを確認できる。

### スクリプトの基礎知識 (色補間とオブジェクトの無効化)
* **Color.Lerp (色の線形補間)**
  * 2つの色と割合 (0.0～1.0) を渡すことで、その中間の色を計算して返すメソッド。HPの割合に応じて「緑 (Full) から赤 (Zero)」へ滑らかに色を変化させるようなUI演出で非常によく使われる。
* **gameObject.SetActive(false) による無効化**
  * オブジェクトのHPが0になった際など、シーンから完全に削除 (`Destroy`) するのではなく、一時的に非表示（無効化）にするメソッド。後で同じオブジェクトを再利用することで、処理負荷を軽減する（オブジェクトプール等）場合によく使われる手法。

## Enemy tank variants (AIとプレハブバリアントの基本)

### NavMesh (ナビゲーションメッシュ) と AIの移動
* **NavMesh とは**
  * AIキャラクターがシーン内で「移動可能なエリア（歩行可能領域）」と「障害物」を認識し、自動的に経路探索 (Pathfinding) を行うためのシステム。
* **Agent Type の設定と自作**
  * NavMeshをベイク（生成）する際、AIの大きさ（半径や高さ、登れる段差など）を定義した「Agent Type」を指定する。デフォルトの Humanoid だけでなく、Navigation設定画面から対象の形状（今回は幅広の戦車）に合わせて独自の Agent Type を新しく作成・調整することができる。
* **Bake時に特定のLayer (Playersなど) を除外する理由**
  * NavMeshのBake（焼き込み）は、地形などの「動かない固定の障害物」を計算する処理である。もしプレイヤー (Players) を含めてBakeしてしまうと、ゲーム開始時のプレイヤーの初期位置が「見えない壁（永久的な障害物）」としてNavMeshに固定されてしまい、AIがそこを通れなくなってしまうため除外する必要がある。

### Prefab Variant (プレハブバリアント) の活用
* **Prefab Variant とは**
  * 既存のプレハブ（ベース）の性質を受け継いだ「派生プレハブ」。ベースの変更（共通スクリプトの更新など）はすべてのバリアントに自動反映されるが、バリアント側で独自に変更を加える（パラメータやモデルの差し替えなど）ことも可能。共通の動作を持ちながらステータスや見た目が異なる「敵キャラクターの量産」などに非常に役立つ。
* **Prefab Override (プレハブのオーバーライドと青い縦線)**
  * バリアントやシーン上のプレハブインスタンスにおいて、ベースプレハブから意図的に数値を変更（上書き）したプロパティの左側には「青い縦線」が表示される。これを Prefab Override と呼び、オリジナルからどこが独自に変更されているかを視覚的に確認できる。
* **Apply All (オーバーライドの適用範囲)**
  * Inspectorの `Overrides` から `Apply All` を実行した場合、変更が保存されるのは「そのオブジェクトが直接リンクしている（大元になっている）プレハブ1つだけ」である。
  * つまり「派生プレハブ（Variant）」を編集して Apply All を押した場合、更新されるのはその派生プレハブのみであり、さらに大元の「ベースプレハブ」までは遡って適用されない。

## Audio mixing (オーディオミキシングと管理の基本)

### Hierarchyウィンドウでの複数選択操作
* **Ctrl / Cmd キーによる個別選択**
  * Hierarchy上で `Ctrl` (Mac: `Cmd`) キーを押しながらクリックすると、離れた場所にある複数のGameObjectを個別に追加・解除して選択（マルチセレクト）できる。
* **Shift キーによる範囲選択**
  * `Shift` キーを押しながらクリックすると、最初に選択したオブジェクトから最後にクリックしたオブジェクトまでの「間にあるすべてのオブジェクト」を一括でまとめて選択できる。

### GameObjectの有効化・無効化 (Is Active)
* **Is Active チェックボックス**
  * Inspectorウィンドウ最上部（オブジェクト名の左隣）にあるチェックボックス。これを外すことで、オブジェクトをシーンから削除せずに「一時的に無効化」できる。
  * 実行中のスクリプトや表示、物理演算などがすべてストップするため、特定の敵AIだけをオフにしてテスト環境を単純化したい場合などに多用される。

### Audio Mixer による音声の一括管理
* **Audio Mixer とは**
  * プロジェクト内のすべての音声をカテゴリー（BGM、エンジン音、SEなど）ごとにグループ分けし、音量やエフェクトをマスター単位で一括管理・調整するための強力なツール。
* **出力先 (Output) のルーティング**
  * 音を鳴らす大元の `Audio Source` コンポーネントにある `Output` プロパティに対し、作成したAudio Mixerの特定のグループ（例: Music, SFX）を割り当てることで、その音がミキサーを経由して鳴るようになる。

### 音量の単位 (dB) とスライダーの概念
* **デシベル (dB) と Attenuation (減衰)**
  * Unityのミキサーにおける音量スライダーは「デシベル (dB)」で計測される。
  * `0 dB` が音源の元の音量（最大）であり、スライダーを下げるとマイナスの値になっていく（Attenuation＝減衰）。
  * 下限（通常 -80 dB付近）に達すると実質的に無音となる。一般的にBGMは -30 dB ～ -20 dB、SE（効果音）は -10 dB ～ -5 dB 程度を目標にミキシングするとバランスが良くなる。

### Audio Ducking (ダッキング効果)
* **ダッキング (Ducking) とは**
  * 特定の重要な音（爆発音やキャラクターの台詞など）が鳴った瞬間に、自動的に他の音（BGMなど）の音量を下げ、重要な音を聞き取りやすくするオーディオ演出の基本テクニック。
* **ミキサーでの実装方法**
  * **ターゲット側 (BGMなど):** 音量を下げたいグループに `Duck Volume` エフェクトを追加する（音を受信する側）。
  * **トリガー側 (SEなど):** きっかけとなるグループに `Send` エフェクトを追加し、Receiveプロパティにターゲット側の Duck Volume を指定する（音を送信する側）。
* **パラメータの調整**
  * `Threshold` (閾値) でエフェクトが発動する音量レベルを決め、`Ratio` でどれだけ音量を下げるかを設定する。`Attack Time` と `Release Time` を 0 に近づけると、SEが鳴った瞬間に瞬時にBGMが下がり、鳴り終わると瞬時に元に戻るメリハリのある動作になる。

## Start menu and Game Manager (UIとゲームフロー制御の基本)

### UIの基盤 (Canvas と EventSystem)
* **Canvas と EventSystem の自動生成**
  * Unityで最初にUI（TextやButtonなど）を作成すると、UIを描画するための `Canvas` とともに、必ず `EventSystem` というオブジェクトが自動生成される。
  * `EventSystem` はマウスのクリックや画面のタップといった「プレイヤーの入力イベント」をUIに伝える心臓部であり、これを誤って削除するとボタンが一切反応しなくなる。
* **UIの位置が画面に正しく表示される理由 (Render Mode)**
  * メニュー画面などのUIは、ワールド空間（3Dのゲーム世界）のY座標を50などに設定して空中に配置したとしても、ゲーム画面には常に正しく最前面に表示される。
  * これはCanvasの標準設定 (Render Mode) が `Screen Space - Overlay` になっているため。3D空間上のどこに配置されていようと、UIは「カメラのレンズの表面（スクリーンの最前面）」に直接張り付くように独立して描画される仕様になっている。作業中のSceneビューを整理するために空中に逃がしているに過ぎない。

### 画面の遷移とイベント (OnClick と SetActive)
* **OnClick () イベント**
  * `Button` コンポーネントの `On Click ()` リストを使用すると、スクリプトを書かずにInspector上の操作だけで「ボタンを押した時の挙動」を設定できる。
* **SetActive(bool) による画面切り替え**
  * OnClickイベントにUIのCanvas自身などを割り当て、`GameObject.SetActive (bool)` を呼び出すことで画面遷移をノーコードで実装できる。
  * TitleCanvasのSetActiveのチェックを外し (False = 非表示)、MenusのSetActiveのチェックを入れる (True = 表示) ことで、タイトル画面からプレイヤー選択画面への遷移が成立する。

### マルチ解像度対応 (Canvas Scaler)
* **Scale With Screen Size**
  * 画面解像度が異なる端末（フルHD、4K、モバイル機器など）でプレイした際、UIが小さくなりすぎるのを防ぐ設定。
  * `Canvas Scaler` コンポーネントの `UI Scale Mode` を `Scale With Screen Size` に設定し、基準解像度 (Reference Resolution) を指定することで、画面サイズに応じてUIが自動的に比例拡大・縮小される。

### オブジェクト操作と階層管理
* **ローカル座標系の正面 (青い矢印)**
  * 移動・回転ツールを `Local` に切り替えた際、表示される **青い矢印 (Z軸)** は常にそのオブジェクトにとっての「正面 (Forward)」を指している。スポーン地点（戦車の初期位置）がどちらを向いているかを確認・調整する際の絶対的な指標となる。
* **Create Empty Parent (空の親オブジェクトの作成) の挙動**
  * 複数のオブジェクト（今回は4つのスポーン地点）を選択して「Create Empty Parent」を実行すると、選択したオブジェクト群の中心座標に新しい親オブジェクトが自動作成される。
  * この際、子になったオブジェクトの**ゲーム内での見た目の位置（ワールド座標）は一切変わらない**が、Inspectorに表示されるTransformの値（ローカル座標）は「新しい親からの相対的な距離」に再計算されるため、数値上は変化する。
* **Visual Tag (Sceneビュー用のカラーアイコン)**
  * スポーン地点などの見えない空のGameObjectに対し、Inspector左上のアイコンメニューからカラータグ（名前付きアイコン）を設定できる。ゲーム画面（Gameビュー）には影響を与えず、Sceneビュー上での位置確認や管理が格段にやりやすくなる。

### ゲームの進行管理 (Game Manager パターン)
* **Game Manager の役割**
  * ゲーム全体の流れ（ラウンドの開始・進行・終了、カメラの制御、勝敗判定、プレイヤーの動的生成など）を統括する専用のオブジェクトおよびスクリプト。特定のオブジェクトに依存しないシステム全体のロジックを集約する設計パターン。

## Bonus features (ポーズ機能とアイテムスポナーの基本)

### UI階層とレイアウトの依存関係
* **親オブジェクトへの依存 (Hierarchy placement)**
  * UI要素（ポーズメニューのプレハブなど）をシーンに追加する際、どの `Canvas` や親オブジェクトの「子」として配置するかが非常に重要になる。
  * UIの位置やサイズ (`Rect Transform`) は「親オブジェクトのサイズやアンカー」を基準に相対的に計算されるため、指定された正しい階層に配置しないと、レイアウトが大きく崩れたり画面外に消えたりしてしまう。

### プラットフォームによる挙動の違い
* **Quit (ゲーム終了) 処理の仕様**
  * ゲームを終了する処理（スクリプトからの `Application.Quit()` 呼び出しなど）は、PC向けなどにビルド（書き出し）された実際のゲームアプリでは正常に機能する。
  * しかし、**Unityエディターでのテストプレイ中**や、**WebGL（ブラウザ向けゲーム）**では仕様上この終了コマンドは動作しない（または無視される）。Quitボタンなどを実装する際は、プラットフォームごとの挙動の違いを考慮しておく必要がある。

### ゲームデザインとシステム設計
* **Spawner (生成管理) パターン**
  * アイテム（パワーアップ）や敵を出現させる際、「Spawner（スポナー / 生成器）」と呼ばれる専用のスクリプトを持たせたオブジェクトをマップ上に配置する手法が一般的。
  * 候補リストからのランダム選出、出現位置の固定、アイテムが取得されてから再出現するまでの待機時間 (`Respawn Cooldown`) などを Spawner 側で独立して管理することで、ゲームバランスの調整やレベルデザインが非常にやりやすくなる。



## C# Scripting (スクリプトの基本と文法)

### 1. Unityスクリプトの基本構造 (MonoBehaviour)
Unityで作成したC#スクリプトは、基本的に `MonoBehaviour`（モノビヘイビア）というクラスを継承して作られます。これを継承することで、GameObjectにコンポーネントとしてアタッチ（追加）できるようになり、Unity特有のイベント関数（StartやUpdateなど）が使えるようになります。

### 2. 変数のアクセス修飾子とInspectorへの表示
Unityのスクリプトでは、変数をInspectorウィンドウに表示して、エディタ上から直接数値を調整したり、オブジェクトを割り当て（アサイン）したりできます。

* **public 変数**
    public float speed = 12f;
  * **特徴:** Inspectorに自動的に表示される。また、他のスクリプトからも自由にアクセス・変更ができる。
  * **メリット:** 記述がシンプルで、初心者向けのチュートリアルでよく使われる。
  * **デメリット:** どこからでも数値を書き換えられてしまうため、プロジェクトが大きくなると予期せぬバグ（意図しないところから変数を変更される）の原因になりやすい。

* **[SerializeField] private 変数 (推奨)**
    [SerializeField] private float speed = 12f;
  * **特徴:** Inspectorには表示されるが、`private` なので他のスクリプトからは直接アクセスできない。
  * **メリット:** 「エディタ上で設定はしたいが、プログラム上は他のスクリプトから勝手に書き換えられたくない」という場合に最適。クラスの独立性（カプセル化）を保てる。
  * **使い分けの実践:** モダンなゲーム開発では、安全性を高めるために「原則として変数は private にし、Inspectorで設定したいものにだけ [SerializeField] をつける」のが主流・ベストプラクティスとされています。

### 3. 主要なイベント関数 (ライフサイクル)
Unityには、特定のタイミングで自動的に呼ばれるメソッド（関数）が用意されています。用途に合わせて使い分けることが重要です。

* **Awake()**
  * スクリプトが読み込まれた直後、ゲーム開始時に一番最初に1回だけ呼ばれる。
  * 主に、自身のコンポーネントの取得（GetComponentなど）や初期化処理に使われる。
* **Start()**
  * `Awake` の後、最初のフレームのアップデート前に1回だけ呼ばれる。
  * 他のオブジェクトへのアクセスや、ゲーム開始時のステータス設定などに使われる。
* **Update()**
  * 毎フレーム（1秒間に数十回、PCのスペックによって変動）呼ばれる。
  * プレイヤーの入力（キーボードやコントローラー）の受け取りや、単純なタイマー処理などに使われる。
* **FixedUpdate()**
  * 一定の時間間隔（デフォルトでは0.02秒ごと）で固定で呼ばれる。
  * **【重要】 Rigidbodyを使った物理演算（移動や力の加算など）は、必ずこの `FixedUpdate` 内で行う。**（Updateで行うと、フレームレートの変動によって動きがカクついたり不安定になるため）。
* **OnEnable() / OnDisable()**
  * オブジェクト（またはコンポーネント）が「有効化 (アクティブ)」になった瞬間、および「無効化」された瞬間に呼ばれる。初期設定やイベントの登録・解除によく使われる。
* **OnTriggerEnter(Collider other)**
  * 自身のCollider、または衝突相手のColliderの `Is Trigger` がONになっている時、物体同士が重なった（すり抜けて接触した）瞬間に呼ばれる。アイテムの取得や弾のヒット判定の基本。

### 4. 参照渡し (refキーワード)
C#において、通常メソッドに引数を渡す際は「値渡し (値のコピー)」となるため、メソッド内でその引数の数値を変更しても元の変数には影響しない。

* **ref の役割:** `ref` キーワードをつけることで「参照渡し (メモリ上の場所を渡す)」となり、メソッド内での値の変更が呼び出し元の変数にも直接反映される。
* **使い方:**
  * メソッド定義側: `void UpdateSpeed(ref float currentSpeed)`
  * 呼び出し側: `UpdateSpeed(ref speed);`
* **注意点:** `ref` で渡す変数は、メソッドに渡す前に必ず何らかの数値で初期化されている必要がある。

### 5. 主要なクラスと構造体 (Mathf, Vector3, Transform)
UnityのC#スクリプトで頻繁に使用される、ゲーム開発に必須の組み込み型。

* **Mathf (数学クラス)**
  * 算術計算に特化した静的 (static) クラス。ゲーム内でよく使われる計算メソッドがまとまっている。
  * 例: `Mathf.Abs` (絶対値)、`Mathf.Clamp` (値の上限・下限の制限)、`Mathf.Lerp` (2点間の線形補間など、滑らかな変化の計算)。
* **Physics (物理):** `Physics.Raycast` (目に見えない光線[レイ]を飛ばし、何かに当たったかどうかの判定や、当たったオブジェクトの情報を取得する。銃の射撃や接地判定で頻出)。
* **Vector3 (構造体)**
  * 3D空間の座標 (X, Y, Z) や、方向、速度などを表すためのデータ型。クラスではなく「構造体 (Struct)」であるため値型として扱われる。
  * よく使う定数が用意されており、`Vector3.zero` は `(0, 0, 0)`、`Vector3.up` は `(0, 1, 0)` などを表す。
* **Transform (クラス)**
  * 全てのGameObjectに必ずアタッチされている基本のコンポーネント（クラス）。
  * オブジェクトの「位置 (Position)」「回転 (Rotation)」「拡縮 (Scale)」の情報を保持し、それらを操作するためのメソッドを提供する。また、親オブジェクト・子オブジェクトといった階層構造（親子関係）の管理も担う。

### 6. ビット演算子 (~0) と NavMesh.AllAreas
UnityのNavMeshや物理演算（Raycast）において、対象とするエリアやレイヤーは「ビットマスク（2進数の各桁をフラグに見立てたもの）」で管理される。
* **`~0` の意味:** `~` はビットを反転させる演算子。`0`（すべてのビットが0）を反転させると「すべてのビットが1」になる。
* **実用例:** `NavMesh.CalculatePath` などの引数で `~0` を渡すことは、「すべてのエリア（全ビットが1のフラグ）」を指定することと同義になる。これはUnityで用意されている `NavMesh.AllAreas` という定数を渡すのと全く同じ意味・挙動である。

### 7. out パラメータとインライン宣言 (out var)
メソッド内で計算した結果を、戻り値（return）とは別に引数経由で受け取るために `out` キーワードが使われる（例: Raycastの衝突情報 `hit` など）。
* **インライン宣言:** 従来はメソッドを呼ぶ前に受け皿となる変数（例: `RaycastHit hit;`）を事前に宣言しておく必要があったが、モダンなC#ではメソッドの引数部分に直接 `out var hit` と記述することで、変数の宣言と結果の受け取りを同時に行える。コードが短くスッキリするため頻繁に利用される。

### 8. コルーチン (IEnumerator と StartCoroutine)
通常のメソッドは呼び出されると1フレーム内で最後まで即座に実行されるが、コルーチンを使用すると「数秒待つ」「別の処理が終わるまで待機する」といった時間軸を伴う処理を複数フレームにわたって実行・一時中断できる。

* **IEnumerator**
  * コルーチンとして動作させるメソッドの戻り値に指定する型。内部で `yield return` を使用することで、処理の一時停止と再開が可能になる。
* **StartCoroutine()**
  * コルーチン処理を開始するための専用のメソッド。通常のメソッドのように直接呼ぶのではなく、`StartCoroutine(メソッド名())` の形で呼び出す必要がある。
* **yield return StartCoroutine(...)**
  * コルーチン内部でさらに別のコルーチンを呼び出し、「その処理が完全に終わるまで、現在の処理を待機させる」ための記述。
  * 例: `RoundStarting` (開始演出) が終わるまで待ち、次に `RoundPlaying` (ゲーム進行) を実行し、終われば `RoundEnding` (勝敗判定) を実行する、といったゲームループ（順序立てた状態遷移）を直感的に記述できる。

### 9. オブジェクトの生成 (Instantiate) と 削除 (Destroy)
* **Instantiate:** `Instantiate(プレハブ, 位置, 回転)` で、実行時に新しいオブジェクトをクローンして生み出す。
* **Destroy:** `Destroy(gameObject)` で、指定したオブジェクトをメモリ上から完全に削除する。第2引数に `Destroy(gameObject, 2.0f)` のように秒数を指定すると、時間差で消滅させることも可能。

### 10. Inspector拡張属性 (Attributes)
変数の上に記述することで、Inspectorの表示を整理・拡張できる機能。
* **[Header("文字列")]**: Inspector上に太字の見出し（カテゴリ名）を表示する。例: `[Header("Damage Reduction")]`
* **[Tooltip("文字列")]**: Inspectorで変数にマウスカーソルを合わせた際、説明文（ツールチップ）を表示させる。チーム開発で変数の意図を伝えるのに役立つ。

### 11. C#の主要な構文 (namespace, foreach)
* **namespace (名前空間):** クラスをまとめる「グループ名」。異なる名前空間であれば、同じ名前のクラスが存在しても衝突しない。他人の書いたコード（ライブラリなど）と機能を切り分けるために使う。
* **foreach:** 配列やリストの中身を最初から最後まで順番に取り出すためのループ構文。`for`文より短く直感的に書ける。

### 12. 高度な設計手法 (ScriptableObject, interface)
* **ScriptableObject:** 大量のデータ（敵のステータス一覧やアイテム図鑑など）をシーンのオブジェクトに持たせるのではなく、Projectウィンドウ上の「データファイル」として独立して保存するための特殊なクラス。メモリの節約に直結する。
* **interface (インターフェース):** 複数の異なるクラスに「共通のメソッド」を持たせるための契約（ルール）。例えば「ダメージを受ける」という `IDamageable` インターフェースを作れば、プレイヤーも敵も木箱も、同じメソッドでダメージ処理を呼び出せるようになる。

## C# for C++ Developers (C++経験者向けのC#の主な違いと注意点)

### クラスとメモリ管理の違い
* **ヘッダファイルがない**
  * C#には `.h` と `.cpp` の分離がない。宣言と実装は常に同じ1つの `.cs` ファイル内にまとめて記述する。
* **アクセス修飾子の書き方**
  * C++の `public:`（ブロック単位）とは異なり、C#では `public int speed;` のようにすべての変数やメソッドの先頭に個別に修飾子を書く必要がある。
* **クラス型変数はすべて「ポインタ (参照型)」**
  * C#において `class` で定義された変数はすべて実体ではなくメモリのアドレスを指す「参照 (Reference)」である。C++のように `*` や `&` を意識して書く必要はないが、代入操作はすべて「ポインタの共有」になる点に注意。
* **コンストラクタには必ず `new` が必要**
  * インスタンスを生成する際は、ローカル変数であっても必ず `new` キーワードを使用してメモリを確保する。
* **配列もオブジェクト**
  * C#の配列はただのメモリの連続領域ではなくオブジェクトである。`int[] arr = new int[5];` のように生成し、`arr.Length` でいつでも安全に要素数を取得できる。

### struct (構造体) と class (クラス) の明確な分断
* C#における `struct` は「値型 (Value type)」であり、代入や関数の引数に渡すと必ず「中身の完全なコピー」が発生する（スタックメモリ）。対して `class` は「参照型 (Reference type)」である（ヒープメモリ）。
* **構造体の値渡しによる不要なコピーを避ける:** `Vector3` などは構造体であるため、関数に渡す際に無駄なコピーを避ける場合は `ref` キーワードを使うなどの工夫ができる。

### プロパティ (Getter / Setter の完全進化系)
C++で手書きしていた `GetSpeed()` や `SetSpeed(float v)` といったカプセル化を、変数のような見た目で美しく記述できる機能。
```csharp
public float MoveSpeed  // ← ① 変数の宣言に見えますが、これは「プロパティ名（関数のまとまりの名前）」です
{
    get                 // ← ② 「値が読み取られたときに呼ばれる関数」の宣言です
    { 
        return moveSpeed; // ③ その関数の中身です（実体変数 moveSpeed の中身を返す）
    }
}
